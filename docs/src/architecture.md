# Architecture

r-bridge is a bridge dApp and a set of reusable primitives. It is **not** a wallet:
native-chain accounts stay in MetaMask (Ethereum), TronLink (Tron) and Keplr
(Cosmos/Agoric). The only key it manages is the rholo account, because the node's deploy
signature is not something those wallets can produce.

```
 MetaMask / TronLink / Keplr            r-bridge web (React)
        │  sign native tx                    │  rholo reads/deploys
        │                                    │  (WASM keystore)
        ▼                                    ▼
 Ethereum / Tron / Agoric  ◄──────►  rholo bridge contracts
   vaults / Agoric vat               current demo: one Bridge contract
        ▲                              planned: BridgeRoot · WrappedToken
        │  unlock tx / vat offer             │  mint deploy
        └──────────── relayer ───────────────┘
          rail undecided: standalone bridge node
          or rholo node add-on (issue #563)
```

The diagram shows the production shape. The relayer box is deliberately generic: neither
the contracts nor the dApp assume where it runs.

## Current vs planned rholo contracts

The working suite is a **single `Bridge` contract** with two inlined libraries:

- `contracts/rholo/src/deploy/00_bridge.rho` — installs the bridge, registers it, and
  defines `balanceOf`, `asset`, `fees`, `withdrawal`, `pendingWithdrawals`, `config`,
  `transfer`, `mint`, `burn`, `completeWithdrawal` and `admin`.
- `contracts/rholo/src/lib/Guard.rho` — m-of-n secp256k1 verification over the 32-byte
  digest.
- `contracts/rholo/src/lib/Ledger.rho` — REV-address identity, balances and fee math.
- `contracts/rholo/build/00_bridge.rho` — generated by `tools/build_contracts.py`; do not
  hand-edit.

The production target splits this into `BridgeRoot` (admin, relayer set, registry, pause),
`WrappedToken` (one per asset), `Bridge` (mint/burn) and `Attestation`. Splitting waits
until the demo's invariants and the native vaults are stable; the wire formats do not
change. See `contracts/rholo/README.md`.

## Identities

- **Native account**: owned by the wallet. The dApp requests signatures; it never sees
  the key.
- **rholo account**: a secp256k1 key handled by the WASM module. It is supplied as an
  encrypted Web3 v3 keystore, can be saved to or loaded from the device, and can be kept
  as an encrypted copy in browser storage (never the password or plaintext). The same key
  addresses an Ethereum account, so a MetaMask key can be turned into a rholo keystore
  and a MetaMask address maps to a REV address without revealing the key. It signs rholo
  deploys and pays phlo.
- **Relayer key**: signs the 32-byte attestation digest. It must be separate from the
  validator key and from the deploy/phlo key.

A bridge transfer binds a native depositor to a rholo recipient (deposit) or a rholo
holder to a native recipient (withdraw). The keys do not have to be the same.

## Trust boundaries

- The wallets are trusted for native signatures only; the dApp explains every
  transaction before the prompt.
- The rholo node is trusted for reads and finality; a second node or the relayer can
  cross-check.
- Relayers are trusted as an m-of-n set. The rholo contract and the native vault verify
  the threshold on-chain, so one compromised relayer cannot mint or unlock.
- The Agoric vat is a smart contract on the Cosmos side; its correctness is part of the
  bridge's trust surface. ERTP/OCapN is the substrate, not a replacement for attestation.
- The treasury is fixed at deployment and can only receive fees; it cannot choose a
  destination.

The threat-by-threat analysis is in [Security model](security.md).

## State and custody

rholo holds the authoritative wrapped ledger: per-asset supply, holder balances,
processed deposit ids, withdrawal records, fees, caps and pause. Native chains hold the
backing assets in a vault (Ethereum/Tron) or a vat account (Agoric). The relayer holds
only a journal of observations and has no custody. A user's native and rholo keys remain
with the user.
