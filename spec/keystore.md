# rholo keystore

The rholo account is the one key the wallets cannot hold for us: MetaMask, TronLink and
Keplr sign their own chains, but none signs a rholo deploy. r-bridge stores that key in a
**Web3 Secret Storage v3** file — the same format r-wallet, r-gen and geth use — so an
account can move between r-bridge and the existing rholo tooling.

Implementation: `crates/rbridge-keystore`, exposed to the browser through
`crates/rbridge-wasm` (`keystore_create`, `keystore_unlock`).

## File format

```json
{
  "version": 3,
  "id": "uuid-v4",
  "address": "<lowercase ethereum address, no 0x>",
  "crypto": {
    "cipher": "aes-128-ctr",
    "cipherparams": { "iv": "<16-byte hex>" },
    "ciphertext": "<32-byte secret, encrypted>",
    "kdf": "scrypt",
    "kdfparams": { "dklen": 32, "salt": "<32-byte hex>", "n": 131072, "r": 8, "p": 1 },
    "mac": "<keccak256 hex>"
  }
}
```

- The key is the 32-byte secp256k1 secret. The same secret addresses a rholo account and
  an Ethereum account; `address` is the Ethereum address, used by v3 tooling as a
  checksum. The REV address (`1111…`) is derived separately by the node.
- `mac = keccak256(derived_key[16..32] || ciphertext)`, checked before decryption.
- New files use r-wallet's work factor: scrypt `n = 2^17`, `r = 8`, `p = 1`.
- Imports accept scrypt **and** PBKDF2-HMAC-SHA256 (geth `--light`) files, and the
  `crypto`/`Crypto` spelling variants.

## Interop

- Files created by r-bridge decrypt in `@ethereumjs/wallet` (the library r-wallet uses);
  verified during development, and the reverse direction is pinned by fixtures under
  `crates/rbridge-keystore/tests/fixtures/` generated by that library.
- `cargo test -p rbridge-keystore` covers create/unlock, wrong password, tampered MAC,
  tampered ciphertext, oversized KDF parameters, the Ethereum address derivation and the
  fixtures.
- `web/src/lib/keystore.test.ts` runs create → unlock through the compiled WASM module.

## Security posture

- The plaintext secret exists only in memory: WASM returns it to the caller for the
  signing operation, and the web app does not write it to storage. Keystore session
  persistence (for example IndexedDB) is deliberately not implemented yet.
- A wrong password and a corrupt file are the same failure: the MAC check happens before
  decryption.
- Imports bound the work a hostile file can request: scrypt memory is capped at 512 MiB
  and PBKDF2 at 10,000,000 rounds, so a crafted `n`/`c` cannot hang or exhaust the tab.
- The password is never logged or stored; the Rust side zeroizes derived keys and
  decrypted buffers where it owns them.
- This is a demo keystore path, not an audited one. Mainnet value moves wait for the
  external audit in the roadmap.
